# Jamia Islamia Abdullah Bin Abdul Muttalib R.A. — masjid appeal website

Fundraising site for Jamia Masjid Syeda Amina R.A. (Malir, Karachi): a home page with the donation panel and bank details, pages for the masjid, construction progress, the Jamia and transparency, and short policy pages. Payments happen on an approved provider's **hosted** page; this site never handles card or bank details.

**Status: preview.** Items not yet verified are marked as placeholders, payments are in `preview` mode (nothing can be charged), and the launch build refuses to run until every item in `npm run check:launch` is resolved.

## Architecture (and why)

| Responsibility | How it is handled |
|---|---|
| Public pages | Static HTML generated by `scripts/build.mjs` from JSON content. Readable without JavaScript; JS only enhances the donation panel, mobile menu and share button. |
| Content editing | `content/site.json` (text, photos, milestones, updates, verified figures). Volunteers can edit it directly on GitHub, or through a Git-based CMS (see "CMS" below). |
| Payments | One approved provider's hosted page/campaign, linked from the donation panel. No server, no secrets, no webhooks in v1. |
| Financial operations | The provider's own dashboard, for authorised finance users only. |
| Public total | Manually reconciled, dated figure in `content/site.json`. Never called "live". |

This is the proportionate option from the brief: a static site linking to a genuine hosted payment page. Choose a Next.js + server integration only if you later need automatic totals or custom checkout sessions (see "Upgrading to a server integration").

## Commands

Requires Node 20+.

```bash
npm install               # fonts (self-hosted) and test tooling
npm run build             # dist/ — preview build: banner, placeholders, noindex
npm run serve             # serve dist/ locally at http://localhost:3000
npm test                  # amount validation, payment-mode guard, escaping, launch rules
npm run check:launch      # list everything still blocking launch
npm run build:launch      # dist/ for production — exits with an error if anything is unverified
npm run preview:file      # preview/index.html — single-file review copy with Placeholders/Sample toggle
npm run check:finance     # confirm bank/payment details match the approved fingerprint
npm run approve:finance   # record changed bank/payment details as approved (finance owner only)
npm run check:security    # injection fuzz test + dependency audit
```

Routes produced in `dist/`: `/` (home, donation panel, bank details, key FAQs), `/masjid/`, `/progress/`, `/about/`, `/transparency/`, `/donate/`, `/privacy/`, `/donation-policy/`, `/donation-status/`.

## Putting it on GitHub and online

1. Create a **private** repository (the bank details and phone numbers are in `config/finance.json`; they are public on the posters, but there is no need to publish the change history).
2. Upload the contents of this folder (including the hidden `.github` folder and `.gitignore`), or from a terminal:
   ```bash
   git init && git add . && git commit -m "Initial site"
   git branch -M main
   git remote add origin https://github.com/YOUR-ACCOUNT/YOUR-REPO.git
   git push -u origin main
   ```
3. In `.github/CODEOWNERS`, replace `@FINANCE_OWNER` and `@TECH_OWNER` with real GitHub usernames.
4. Settings → Branches → add a rule for `main`: require a pull request, require review from Code Owners, require the `checks` status check to pass, and block force pushes.
5. Settings → Code security: turn on Dependabot alerts and secret scanning.
6. Hosting (Cloudflare Pages or Netlify): connect the repository, build command `npm ci && npm run build`, output folder `dist`. `dist/_headers` applies the security headers on both. Switch to `npm run build:launch` only when `npm run check:launch` reports nothing left.
7. Turn on two-step login for every GitHub, hosting and domain account, and lock the domain at the registrar.

## Payment modes

Set in `config/finance.json → payments.mode`. The site decides the **effective** mode with `resolvePaymentMode()` and always falls back to a safer mode:

| Mode | When it actually runs | What the donate button does |
|---|---|---|
| `preview` | Default, or whenever anything below is missing | Validates the amount and shows what *would* be sent to the provider. Nothing is charged; no success state. |
| `test` | `provider` set and `testUrl` is an https sandbox/test page | Opens the provider's sandbox page with a "Test mode" notice. |
| `live` | `provider`, `currency`, `liveUrl`, organisation name set **and** `recipientVerified: true` **and** `accountApproved: true` | Opens the live hosted page. |

Amount handoff: only set `amountHandoff.supported: true` if the provider genuinely accepts an amount in the URL (give `param`, and `unit` `minor` or `major`). Otherwise the preset buttons disappear and the donor chooses the amount on the provider's page, so the site never shows a selector the provider would ignore. Monthly giving appears only when `recurring.enabled` is true and a cancellation policy is set.

`/donation-status/` is a neutral return page. It never claims a payment succeeded; the provider's confirmation is the record.

### Choosing a provider

The provider must accept *the collecting organisation*, its country, its settlement account and this fundraising activity. Stripe and Mollie are examples, not defaults: Stripe's availability list does not include Pakistan for ordinary direct accounts, and Mollie serves organisations in the EEA, Switzerland or UK with an IBAN/UK account. A Pakistani organisation needs a local or international service that explicitly accepts it. Check current terms on the provider's official site before applying. Never use a personal account or someone else's organisation.

## Currency minor units

Amounts are stored as integers in the currency's ISO 4217 minor unit (PKR 1,000 = `100000` paisa). `src/lib.js` overrides the browser's display rules where they differ from ISO 4217 (PKR, IDR, HUF and a few others). Confirm the unit your payment provider expects before going live.

## Security notes

- **Bank-detail lock.** `config/finance.lock.json` holds a SHA-256 fingerprint of everything in `config/finance.json` (bank accounts, IBANs, wallets, payment mode, provider links, approved hosts). Every build checks it; if anyone changes an account number without approval, the build stops and nothing is published. To approve a genuine change: confirm it by phone with the Muhtamim on a number you already know (never from the message asking for the change), run `npm run approve:finance`, and merge through a pull request reviewed by the finance owner.
- **Approved payment hosts.** The donate button only ever sends donors to a domain listed in `payments.allowedHosts`. The list is empty until a provider is approved, so the site stays in preview/test.
- **Content is escaped; links are checked.** Every text field is HTML-escaped. Links and image paths from content must be `https`, `mailto:`, `tel:` or a relative path; `javascript:`, `data:`, `http:` and protocol-relative links are dropped. `npm run check:security` proves this by rendering all pages with attack strings.
- No secrets exist in this project. If a server integration is added later, keep keys in the host's secret store, never in the repo or client bundle.
- `dist/_headers` sets CSP, HSTS, nosniff, referrer and permissions policies on Netlify/Cloudflare Pages. Mirror them on other hosts. The CSP allows only same-origin scripts, styles, fonts and images.
- No analytics, advertising pixels, newsletter or donor accounts. Add none without a concrete need and a consent arrangement.
- Photos: re-export at ≤2400px, strip EXIF/GPS (e.g. `exiftool -all= photo.jpg`), save as JPEG/WebP into `media/` and reference them as `"src": "media/…"`, with alt text, date, `type` (`actual` or `design`) and rights noted in `content/site.json`. Site photos go in `buildingToday.photos`, oldest first; the newest one also appears on the home page.
- Enable MFA on the domain registrar, host, GitHub and payment-provider accounts. Give each person their own login.

## CMS

`content/site.json` is the CMS data. Two options:

1. **Edit on GitHub** (simplest): editors change the JSON in the web editor and open a pull request; the host rebuilds on merge.
2. **Git-based CMS** (friendlier forms): e.g. Decap CMS or Sveltia CMS, configured to edit `content/site.json` only. Do **not** expose `config/finance.json` in the CMS. CODEOWNERS plus branch protection makes finance changes require the finance owner's approval.

## Upgrading to a server integration (only if needed)

If you later want automatic totals or checkout sessions created by the site: move to a framework with server routes (e.g. Next.js), create checkout sessions server-side with the provider's official SDK, verify webhooks with the provider's signature, store processed event IDs idempotently, count each successful payment once (monthly gifts per received instalment), and apply refunds/reversals. See the build brief §H for the full list. `src/lib.js` (`parseAmount`, `currencyExponent`) can be reused for server-side validation.
